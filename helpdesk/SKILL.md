# Helpdesk

作为技能体系的导航与支持层，把用户的工作需求映射到当前最合适的技能，并解释选择依据。以当前环境提供的技能目录及技能自身说明为准，不维护容易过时的静态技能清单。

## 判断用户真正需要什么

先从请求中提取：

- **Outcome**：用户最终想得到的结果，而不只是他使用的动词。
- **Artifact**：代码、文档、表格、演示、图片、研究结论、方案或其他交付物。
- **Stage**：探索、澄清、设计、实现、验证、评审、修复或交付。
- **Method**：用户明确要求的方法，例如 TDD、原型、实时控制或后台研究。
- **Constraints**：目标应用、文件格式、仓库上下文、时效性、权限及副作用。

用户明确指定技能时，优先尊重其选择。只有该技能无法完成目标、缺少必要前置条件或会明显越过职责边界时，才解释问题并建议重新路由。

## 建立候选集

使用当前上下文中的可用技能目录作为 source of truth：

1. 先依据技能的 `name` 和 `description` 缩小到一至三个候选。
2. 当候选边界、前置输入或 handoff 仍不清楚时，完整读取这些候选的 `SKILL.md`；不要为一次选择加载整个技能库。
3. 同时匹配目标产物、工作阶段和用户指定方法。名字相近不是充分理由。
4. 检查候选的排除条件。一个技能能接触某类文件，不代表它适合当前动作。

不得假设目录中不存在的技能或能力。没有精确匹配时，明确指出能力缺口，并给出最接近的可行路径；只有用户希望扩展技能体系时，才建议创建或安装新技能。

## 作出路由决策

选择满足目标所需的最小技能集合：

- **单一技能**：一个技能能够端到端完成当前工作时，只推荐它。
- **顺序工作流**：需求确实包含不同阶段时，给出必要的技能链，并标明现在从哪一个开始以及进入下一阶段的条件。
- **并行工作**：只有任务可独立拆分且并行会带来实际收益时，才建议并行技能。
- **需要澄清**：不同答案会改变技能选择或产生明显成本、风险、外部副作用时，提出一个最小问题。否则采用最合理的假设并明确说明。

不要为了展示技能体系而输出完整生命周期。只列出完成当前需求真正需要的技能；后续技能尚未成为必要步骤时，将其作为条件式建议。

## 回答方式

用户只是在咨询、比较或排障时，保持只读并给出紧凑的 route card：

```markdown
**建议：** `<skill-name>`
**原因：** 它如何匹配目标、产物和当前阶段。
**需要提供：** 开始工作所需的最小输入。
**下一步：** 用户如何调用，或可以立即继续做什么。
```

存在有竞争力的替代项时，再补充一项 `备选` 及其适用条件。多技能工作流用箭头表示，并解释每个 handoff 的完成条件。

用户询问某个技能为何被选中、为何没有触发、两个技能有什么区别、需要哪些输入或能否组合时，应以相关技能当前的 description 与 `SKILL.md` 为证据直接回答。区分：

- **能力边界**：技能负责什么结果。
- **触发条件**：什么请求应让它被选择。
- **前置条件**：开始前必须已有的信息或状态。
- **交付与 handoff**：它在哪里结束，下一技能何时接手。

如果用户的原始消息是在请求完成工作，而不只是询问技能，先用一两句话说明路由，然后立即按被选技能执行；不要要求用户重复请求。执行下游技能前，完整读取其 `SKILL.md` 并遵循其中约束。

## 完成标准

当推荐技能与用户的 outcome、artifact、stage、method 和 constraints 一致，选择依据可由当前技能说明验证，必要输入与下一步明确，替代项和不确定性只在会影响决策时出现，并且没有让用户重复已经提供的信息时，helpdesk 工作完成。
