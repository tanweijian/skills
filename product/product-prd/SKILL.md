# Product PRD

把已经足够明确的产品决策固定成一份能被产品、设计、工程和测试共同消费的需求契约。PRD 说明 why、who、what 和验收目标，不替代 `product-digging` 的问题探索、`product-prototype` 的体验验证，也不替代 `code-spec` 的技术设计。

## 输入与就绪门槛

优先使用以下来源，发生冲突时保留冲突并指出需要谁作出决定：

1. 用户在当前请求中明确的目标、范围和取舍
2. 已批准的产品决策、用户研究或业务证据
3. 现有 PRD、原型结论、issue 或其他项目文档
4. 为推进工作而采用的非阻塞 assumption

开始编写前，确认至少有：

- 目标用户、使用场景和要解决的问题
- 期望结果或价值，以及本轮要改变的用户行为
- 核心流程、关键状态、主要成功路径和必须处理的失败路径
- in-scope、out-of-scope、平台或业务约束
- 能判断交付是否满足需求的 acceptance criteria

只在缺口会改变产品行为、范围、成本或验证方式时阻塞。目标用户、问题或价值仍不清楚时返回 `product-digging`；核心流程或状态存在需要比较的方案时返回 `product-prototype`。不要用猜测填掉会改变契约的选择，也不要因为缺少非关键细节而停住。

区分三种状态：

- **Decision**：已有明确来源并被接受的产品选择，可以写成要求。
- **Hypothesis**：仍需原型或真实用户证据验证的判断，不当作已验证结果。
- **Assumption**：为继续编写而暂定的非阻塞前提，注明影响和验证方式。

## 1. 建立产品契约

先用一段简洁的问题陈述说明当前状态、目标用户、触发场景和期望改变。把“用户想要某个方案”与“该方案解决了什么问题”分开记录；方案不是问题证据。

建立 decision ledger，至少记录来源、状态、影响范围和待确认人。若已有原型，读取其任务流程、状态和观察结论；可运行不等于假设已成立，原型限制也要传递到 PRD。

## 2. 固定目标与范围

明确本版本的 outcome、非目标和成功信号：

- **In scope**：本次必须交付的用户行为、规则、状态和平台边界。
- **Out of scope**：明确排除的角色、入口、平台、数据、自动化或后续能力。
- **Success signals**：能观察的行为或业务结果。只有有来源时才写 baseline、target、时间窗和口径，不凭空制造数字。

将依赖、权限、合规、隐私、可访问性、国际化或性能约束写成产品约束；若没有影响本需求的约束，明确记录 `None identified`，不要泛化成技术清单。

## 3. 描述任务与状态

以用户任务为主线组织入口、前置条件、操作、结果和下一步。用状态表或状态机表达会影响判断的行为，至少覆盖：

- 初始、空态、加载或不可用状态
- 用户动作及其前置条件
- 成功结果、持久化或可见反馈
- 校验失败、权限不足、网络或部分失败
- 取消、重试、恢复、返回和重复操作

说明每个状态用户能看到什么、能做什么、不能做什么，以及系统应保持的产品不变量。保持术语、实体和状态在列表、详情、通知及结果页一致。只写用户需要理解或验收的行为，不指定组件、类、数据库表或实现步骤。

## 4. 编写可验收的需求

为每条 requirement 分配稳定 ID（如 `R1`、`R2`），一条只表达一个可验证的行为。使用“角色 + 触发/前置条件 + 必须结果”的句式，避免 `友好`、`快速`、`支持一切` 这类不可观察的词；若确有质量目标，给出测量口径或明确标为待定。

建议为每条需求补充：

- 关联用户任务和优先级（Must / Should / Could，或沿用项目既有术语）
- 正常路径及至少一个会改变结果的边界或失败条件
- 与其他需求、约束或假设的依赖
- 对应的 acceptance criteria ID

验收标准写成可复现的观察，优先使用 `Given / When / Then`；同一标准不要同时验证多个无关行为。覆盖成功、拒绝、空态和恢复等会影响发布判断的分支，并确保不依赖内部实现细节。

## 5. 检查风险与一致性

提交前做一次产品自检：

- 每条 in-scope 行为都有 requirement 和 acceptance criteria。
- 每个关键状态都有进入条件、可见反馈和退出或恢复路径。
- 角色、权限、数据边界和敏感信息处理没有互相矛盾。
- out-of-scope 没有通过“以后再说”的模糊措辞隐藏范围。
- 假设、hypothesis、依赖和风险都标有证据或验证计划。
- 指标、错误文案、时间或数量限制等具体数字都有来源；没有来源就写 `TBD` 并指出决策者。

发现目标用户、问题或价值被新证据推翻时，返回 `product-digging`；发现只是交互或状态方案未决时，返回 `product-prototype`。工程反馈若要求改变产品规则，更新 PRD 中的 decision 和 acceptance criteria，不把技术取舍静默写成产品决定。

## 6. 交付与 handoff

用户未指定存放位置时，遵循仓库既有文档约定；没有约定则在回复中提供完整 PRD，并说明尚未持久化。不要未经要求创建外部 ticket、排期、发布或通知。需要落盘时读取 [references/prd-template.md](references/prd-template.md)，按模板保留最小但完整的字段。

交付内容至少包括：

- PRD 位置或完整正文、版本和状态（`Draft` / `ReadyForHandoff`）
- 已确认的目标、范围、决策、requirements 与 acceptance criteria
- 未决的 open questions、assumptions、hypotheses、依赖和风险
- 证据来源、成功信号及尚未验证的指标
- 下一步所需输入和 handoff 目标

当所有阻塞性产品选择已解决、in-scope requirement 可逐条验收、关键状态和边界可追溯、open questions 均不阻塞工程理解时，标记为 `ReadyForHandoff`，交给 `code-proposal` 或用户指定的下一阶段。仍有会改变行为的 blocking question 时保持 `Draft`，不要声称 PRD 已就绪。

## 完成标准

PRD 完成意味着产品契约清晰且可追溯，不意味着问题已经被用户验证或代码已经实现。完成时，读者应能回答：谁在什么场景下要完成什么任务、系统如何响应每个关键状态、哪些内容本次不做、什么观察算通过，以及哪些事项仍需明确。
