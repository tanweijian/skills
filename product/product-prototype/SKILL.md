# Product Prototype

用最小可体验原型消除 Behavior / Experience 的不确定性。交付物是可检查的体验、验证证据与待决事项；原型可运行不等于产品假设成立，也不等于已具备生产上线条件。

## 输入与职责边界

优先沿用用户要求、已有产品资料、`product-proposal` 的 route decision、需求挖掘结论、现有 PRD 和原型反馈。提取目标用户、使用场景、要验证的 hypothesis、范围、约束与可观察的验证目标，不要求补齐完整 PRD 才能开始。

区分已确认的 decision、待验证的 hypothesis 和为推进原型采用的 assumption。缺失信息只有在会实质性改变核心体验、范围或验证方式，且无法合理推断时才提出最小阻塞问题；其余假设明确标注后继续。

目标用户、问题或价值不清楚且阻塞方案判断时，返回 `product-digging`；用户只要求展示一个已选方案时，尊重其选择，将未验证项列为限制，不强制开展需求访谈或方案比较。

本技能可以编写演示代码，但其目的限于体验验证。真实支付、发送消息、修改业务数据等操作优先模拟；需要连接真实系统、发布或邀请测试参与者时，先确认相应授权。生产实现仅在用户要求时交给 `code-proposal`。

## 1. 确定验证目标

把原型要帮助做出的产品决策与可观察行为连接起来：

```text
Hypothesis → 使用任务 → 原型覆盖 → 观察信号 → 决策依据
```

例如，“用户能理解批量操作的影响”应落到选择对象、检查影响、确认或取消的任务，观察是否误选、能否解释结果以及能否恢复，而不是仅检查按钮能否点击。

明确本轮 in-scope / out-of-scope、已有基线和成功或失败的判断依据。有量化阈值时注明来源；缺少真实样本时用定性观察，不凭空给出转化率、满意度或验证通过率。

完成本步骤时，应能说明原型验证哪个决策、谁在什么场景下完成什么任务，以及什么观察会支持、反驳或不足以判断该假设。

## 2. 选择最小原型形态

按验证目标选择保真度和载体，沿用用户指定的工具、平台与已有项目约定：

- 信息组织、流程顺序或概念理解：线框、故事板或可点击低保真原型。
- 交互、状态变化或任务完成：可运行的交互原型，用 mock / fixture 覆盖所需行为。
- 视觉层级、品牌表达或细节体验：在相关页面提高视觉保真度，保持核心流程可检查。

只实现对观察有贡献的页面与行为。比较方案时保持任务、数据和验证方式可比，并说明真正不同的产品决策；用户已经选定方案时直接深化该方案。

已有 codebase 时先检查相关界面、组件、样式、运行方式和仓库规范，复用能支持验证的结构。没有既有技术约束时选择易于本地体验的最小载体，不为原型引入无关的架构、服务或迁移。

完成本步骤时，载体、保真度、关键页面、模拟边界及其选择理由应足以指导制作。

## 3. 制作可体验的任务闭环

围绕用户任务组织入口、操作、结果与必要的返回或恢复路径。建立一致的术语、信息层级与主要操作，让用户通过界面理解下一步，而不是依赖演示者解释。

对影响验证判断的节点，明确：

- 用户可见信息、可执行动作及前置条件。
- 操作引发的状态变化、结果反馈和取消或恢复行为。
- 相关的空态、加载、成功、失败、校验或权限状态；仅覆盖本轮任务需要的分支。

使用可信且一致的示例数据，避免敏感真实数据。模拟提交应产生一致的可见结果；同一实体在列表、详情和结果页保持一致。提供适合复测的初始状态或重置方法，并说明刷新后的数据保留行为。

将实际可操作功能与仅用于展示的部分区分开。对未实现的入口禁用或明确标注；mock、人工代执行和外部系统替代均记录为原型限制。若性能、真实数据或服务可靠性本身是验证对象，说明模拟无法回答哪些问题。

完成本步骤时，in-scope 任务可从明确的初始状态走到可观察结果，关键分支可触发，且模拟边界不会被误认成真实能力。

## 4. 检查原型与验证假设

分别记录两类结果：

**Artifact check**：原型是否按设计工作。用当前可用的预览、浏览器或测试工具实际走通核心任务，检查关键分支、状态一致性和必要的键盘操作、焦点与目标视口表现。修复阻碍体验的错误，再重复受影响的路径。静态检查或构建通过仅能支持对应结论，不能替代交互检查；工具不可用时说明未检查项。

**Product validation**：方案是否支持产品假设。已有用户反馈或获准开展测试时，给参与者场景与任务，避免提示点击位置；记录观察到的行为、原始反馈来源、困惑与恢复过程。没有真实参与者时，可以做启发式检查或模拟走查，但明确其证据等级，不声称已经过用户验证。

对每个 hypothesis 记录结果：支持、反驳或证据不足，并注明证据与适用范围。将观察事实与解释分开；完成任务不自动证明用户需要该功能，少量样本也不代表总体偏好。

发现问题后优先修复影响当前决策的体验障碍，保持迭代范围可控。反馈改变目标用户、问题或原型范围时，先说明变化并重新判断路由，不静默扩展本轮工作。

## 5. 交付与 handoff

交付可体验的文件、预览或原型链接，并说明启动方式、入口任务、初始数据与重置方法。遵循用户指定或仓库已有的存放约定；无约定时使用独立、可识别的原型目录，避免覆盖生产入口。工具无法生成或打开原型时，如实交付当前产物与阻塞项，不把设计说明当成已运行的原型。

随原型提供紧凑记录；简单任务可放在回复中，复杂原型可附在约定位置：

- **Goal / Scope**：目标用户、场景、验证问题与本轮边界。
- **Prototype**：产物位置、体验方式、关键路径及模拟限制。
- **Evidence**：实际执行的检查、观察来源、hypothesis 结论与未验证项。
- **Decisions / Open questions**：已确认决策、候选建议、剩余风险和需要用户取舍的事项。
- **Next step**：继续验证、返回需求挖掘，或满足条件后固定需求；用户只要求原型时在此结束。

结论推翻问题或价值假设时，交回 `product-digging`；核心行为足以固定且用户要求需求文档时，交给 `product-prd`。Handoff 携带任务流程、关键状态和规则、证据、已确认决策、模拟限制及 open questions；未经确认的建议仍标为候选方案。

执行下游前，依据可用技能目录确认能力并完整读取对应说明。同仓库文件可通过 [product-digging](../product-digging/SKILL.md)、[product-prd](../product-prd/SKILL.md) 和 [code-proposal](../../code/code-proposal/SKILL.md) 定位；路径存在不代表技能已安装或说明完整。下游不可用时说明能力缺口，不自行创建或安装，也不声称已完成交接后的工作。

## 完成标准

当 in-scope 任务闭环已交付、关键状态与模拟边界明确、实际完成的检查及未检查项如实记录、每个验证假设都有证据结论或“待验证”状态，并且已确认决策与后续事项可追溯时，本轮原型工作完成。没有真实反馈不阻止交付原型，但产品验证仍标为待验证；只有真实观察才可作为用户验证证据。
