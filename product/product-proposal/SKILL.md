# Product Proposal

先判断产品工作处于哪个阶段、需要消除哪类不确定性，再交给最合适的 product skill。本技能负责 route decision、最小上下文整理和 handoff；交付物是路由决策，而不是产品提案文档，不替代下游的需求挖掘、原型验证或 PRD 编写。

## 入口原则

未明确指定子技能的 product request 先经过本技能。用户显式调用 product 子技能时尊重该选择；只有前置条件缺失或职责不匹配时，说明原因并重新判断路由。

使用用户要求、已有产品资料、访谈或使用证据、原型反馈和当前 PRD 作为判断依据。只读取足以做出 route decision 的上下文；区分已确认的 decision、待验证的 hypothesis 和非阻塞 assumption，证据缺失不等于问题不存在。

Product 决定 why、who、what 与验收目标；Code 决定如何实现和验证。纯代码工作交给 `code-proposal`；若技术请求暴露出尚未决定的产品行为，先路由到对应产品阶段。

## 1. 分类请求与不确定性

从已有上下文提取目标产物、当前阶段、用户指定方法，以及足以改变路由的关键缺口：

- **Problem / Value**：目标用户、使用场景、实际问题、现有替代方式，以及解决问题的价值是否明确。
- **Behavior / Experience**：核心流程、交互、状态与异常路径是否已决定；是否需要通过原型比较或验证方案。
- **Requirement / Contract**：范围、产品规则、约束与 acceptance criteria 是否足以形成可交接的需求。

把“用户提出了一个功能方案”和“该方案解决的问题已确认”分别记录。用户已经明确目标与取舍时沿用其决策；只有会影响当前交付的缺口才触发补充探索。

完成本步骤时，应能说明用户现在要什么、已有输入支持什么，以及哪个未决问题决定下一步。

## 2. 选择最小路由

| 当前请求或关键缺口 | 下一技能 | 交接输入与进入条件 |
| --- | --- | --- |
| 探索想法、挖掘需求；目标用户、问题或价值尚不清楚 | `product-digging` | 想法、已知场景与证据、待澄清的问题和约束；允许从模糊输入开始 |
| 用户要求产品原型，或需要验证流程、交互、状态和方案差异 | `product-prototype` | 目标用户与场景、要验证的 hypothesis、原型范围及可观察的验证目标；未决行为可作为验证对象 |
| 编写或更新 PRD；目标与核心行为已明确，需固定需求和验收目标 | `product-prd` | 已确认的产品决策、scope / out-of-scope、约束、已有需求或原型结论；阻塞性产品选择已解决 |
| 已有明确产品契约，用户要求工程实现 | `code-proposal` | 当前 PRD 或等价的用户要求、acceptance criteria、范围、产品约束与未决问题 |

用户只要求某个产物时，选择完成该产物所需的路径，并在该产物完成后结束。已有输入足够时直接进入目标技能，不要求用户重复前一阶段。

混合请求按依赖排序：问题与价值的不确定性阻塞方案判断时先 digging；问题明确但行为需要验证时先 prototype；核心行为明确后由 PRD 固定需求。Prototype 是条件分支，不是每份 PRD 的必经步骤。

下游发现未决产品选择时，按缺口重新路由。原型结论若推翻问题假设，返回 digging；只影响交互或规则时，继续验证或更新 PRD。给出后续阶段时，同时说明进入条件，不把预想路径当成已完成工作。

## 3. 检查下游能力与前置条件

选定下一技能后，依据当前可用技能目录及仓库说明确认其能力，执行前完整读取其 `SKILL.md`。同仓库的入口文件位于：

- [product-digging](../product-digging/SKILL.md)
- [product-prototype](../product-prototype/SKILL.md)
- [product-prd](../product-prd/SKILL.md)
- [code-proposal](../../code/code-proposal/SKILL.md)

这些路径用于定位说明，不代表技能已安装或具备可执行能力。技能不可用、文件仍为占位内容或实际说明与预期不符时，保留 route decision，明确能力缺口和可行下一步；不声称已经调用或完成下游工作，也不自行创建或安装技能。

路由已明确时直接说明并继续用户请求范围内的下游工作。只有缺失信息会实质性改变范围、成本、产品行为或验证方式，且无法从上下文合理判断时，提出一个最小阻塞问题。普通需求细节交给对应子技能处理，路由阶段不开展完整访谈。

## 4. 输出 route decision 与 handoff

交接前给出紧凑的 route decision；信息简单时用一两句话表达，复杂请求可用：

```markdown
**Request type:** 产品原型
**Route:** product-prototype；验证结论足以固定需求后可进入 product-prd
**Reason:** 用户与问题已明确，核心交互仍有两个待比较方案
**Contract:** 当前用户要求及已有产品资料
**Assumptions / Open questions:** 有依据的假设、待验证问题与阻塞项
**Next input:** 验证 hypothesis、场景、原型边界和观察目标
**Execution status:** 已交接 / 等待输入 / 下游技能不可用
```

Handoff 携带下游真正需要的目标、证据来源、已确认决策、范围、约束与未决问题。已有 artifact 使用路径或链接引用；原型观察与用户反馈作为证据传递，未经确认的方案继续标为 hypothesis。

只有用户要求工程实现且产品契约足够明确时，才交接 `code-proposal`，由它选择代码流程。产品原型按验证范围执行，不自动升级为生产实现；交接本身也不授权发布、创建外部 ticket 或承诺开发排期。

## 5. 重新路由

用户改变目标用户、问题、范围或 acceptance criteria，验证结果推翻关键假设，或工程反馈揭示产品规则冲突时，重新评估受影响的阶段。

保留未受影响的决策与证据，说明变化为何改变 route。工程反馈提出技术限制时，把限制带回产品阶段供取舍，不把技术建议静默改写为已确认的产品要求。

## 完成标准

请求类型、选定 route、选择依据、已知 contract、关键未决问题和下一技能输入均已明确，且下游执行状态与 blocker 如实说明时，路由完成。路由完成不代表需求已验证、PRD 已就绪或实现已完成。
